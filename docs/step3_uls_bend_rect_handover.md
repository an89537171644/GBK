## 3. Объём, разрешённый для рассмотрения

Версия 1 рассматривает только:

- обычное прямоугольное сечение при одноосном изгибе без `N`;
- тяжёлый бетон B15–B40;
- ненапрягаемую арматуру A400/A500 provisional-профиля;
- один ряд растянутой арматуры и `As_prime=0`;
- явные локальные оси, ось момента и растянутую грань;
- контекст `short` для сквозного design/dataset/ML;
- контекст `long` (`gamma_b1=0,9`) только для изолированной проверки изгиба;
- безопасную остановку при невыполнении `x<=xi_R*h0`.

Все перечисленные сужения должны быть подтверждены инженером. Двойное
армирование, многорядная геометрия, продольная сила, косой изгиб,
предварительное напряжение и специальные воздействия не входят в передачу.

## 4. Обязательные инженерные проверки

Инженеру предлагается не подтверждать реализацию до выполнения всех пунктов:

1. Сверить профиль СП, изменения № 1 и № 2 и точность ссылок на пп. 6.1.12,
   6.1.20, 6.2.8, 8.1.1, 8.1.3–8.1.6, 8.1.8–8.1.9 и 8.1.12.
2. Построчно проверить рабочий каталог B15–B40 и A400/A500; отдельно
   подтвердить строку B15 и разрешить противоречие пяти A400-значений
   390/340 МПа с базовыми таблицами 6.13–6.14 (400/350 МПа).
3. Подтвердить трактовку `short/long` и применение `gamma_b1` к `Rb` вместе с
   выбором `Rsc`.
4. Проверить локальные оси, растянутую грань, семантику `cover` и получение
   `h0` для обеих ориентаций.
5. Подтвердить проектное сужение `As_prime=0` и запрет произвольных
   `h0_override`/`Rsc_override`.
6. Убедиться, что BMR-05 не публикует способность вне применимости и не
   выполняет безусловную подстановку по п. 8.1.12.
7. Независимо, без вызова проверяемого ядра, воспроизвести BMR-01—BMR-05 и
   подписать исходные данные, промежуточные значения и результаты.
8. Проверить, что непокрытый п. 8.1.3 приводит к `incomplete`, а узкий `pass`
   не открывает проектный шлюз.
9. Утвердить единую политику численных допусков; допуск не должен менять
   расчётный исход.
10. Выполнить реальное внешнее сопоставление в эквивалентной расчётной модели.

## 5. Технические доказательства ветви

На окончательном состоянии ветви исполнитель должен приложить полный вывод:

```text
python -m pytest
ruff check .
python -m sp63_core validate --golden
python -m sp63_core validate --generate-dataset-limit 20 --json
python -m sp63_core generate-dataset --limit 20 --load-duration short --split --group-split --output-dir data/generated --prefix smoke_dataset --report reports/interim/smoke_dataset_report.json
python -m sp63_core train-baseline --generate-dataset-limit 50 --model-output models/smoke_baseline.pkl --metrics-output reports/interim/smoke_baseline_metrics.json
git diff --check
git status --short --branch
git rev-parse HEAD
```

Pre-commit прогон на K108 дал `854 passed in 37.34s`. После commit-aware
переноса на K109 полный прогон дал `843 passed, 20 failed in 46.26s`; все 20
отказов каскадно связаны со штатным `protected-files-check`, обнаружившим
изменения шести защищённых файлов расчётного и доказательного контура.
`ruff check .` и `git diff --check origin/main...HEAD` завершились успешно.

Такой исход является обязательной остановкой перед утверждением нормативных
формул: тесты guard и зависимые агрегированные проверки нельзя изменять ради
получения формального зелёного статуса. Ветвь передаётся только как draft PR,
а слияние запрещено до независимого инженерного решения.

`validate --golden` должен сообщать `12/12`: семь прежних инфраструктурных
случаев и BMR-01—BMR-05. Та же матрица передаётся в acceptance gate; это не
повышает доказательный статус BMR выше `ASSUMPTION`.

Dataset/ML smoke-команды создают только синтетические технические артефакты.
Они проверяют контракты версии 0.3 и fail-closed guards, но не создают
нормативное evidence и не меняют `project_use=false`.
